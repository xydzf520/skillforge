## 1. 测试用例编写规范

### 1.1 覆盖原则

lint 规则 `check_test_coverage` 要求：**测试用例数 >= 分支数**。但这只是最低要求。生产级 Skill 的测试应该覆盖：

| 类型 | 说明 | 优先级 |
|------|------|--------|
| 正常路径 | 每个分支的典型输入 | 必须 |
| 边界值 | 恰好在阈值上的输入 | 必须 |
| 异常输入 | 缺字段、类型错误、空值 | 必须 |
| 极端值 | 超出正常范围的巨大/微小值 | 推荐 |
| 多条件组合 | 多个参数同时在边界上 | 推荐 |

### 1.2 测试用例结构

每个测试用例包含三部分：输入数据、期望输出、断言规则。

```markdown
### 正常投诉率场景

**输入:**
```json
{
  "total_sessions": 10000,
  "valid_sessions": 7800,
  "complaint_categories": {
    "质量问题": 30,
    "充电问题": 15,
    "退款退货": 50
  },
  "complaint_alert_threshold": 5.0
}
```

**期望输出:**
```json
{
  "step_3_conclusion": "绿灯",
  "max_complaint_pct": 0.5,
  "alert_triggered": false
}
```

**断言:**
- `output.step_3_conclusion == "绿灯"`
- `output.max_complaint_pct < complaint_alert_threshold`
- `output.alert_triggered == false`
```

### 1.3 必须覆盖的五类测试场景

#### 场景一：每个分支至少一个用例

确保决策树的每条路径都被测试过。如果 Step 3 有三个分支（红/黄/绿），就至少要有三个测试用例分别命中。

#### 场景二：阈值边界

```markdown
### 边界值_投诉率恰好5%

**输入:**
```json
{
  "total_sessions": 1000,
  "complaint_categories": {
    "质量问题": 50
  },
  "complaint_alert_threshold": 5.0
}
```

**期望输出:**
```json
{
  "step_3_conclusion": "红灯",
  "max_complaint_pct": 5.0,
  "alert_triggered": true
}
```

**断言:**
- `output.max_complaint_pct >= complaint_alert_threshold`
```

#### 场景三：数据缺失

```markdown
### 数据缺失_零轮对话占比过高

**输入:**
```json
{
  "total_sessions": 1000,
  "zero_round_sessions": 600,
  "valid_sessions": 400
}
```

**期望输出:**
```json
{
  "step_1_conclusion": "数据质量差",
  "valid_ratio": 0.4,
  "proceed_to_step_2": false,
  "message": "0轮对话占比过高，建议排查机器人接待比例"
}
```
```

#### 场景四：极端值处理

```markdown
### 极端值_首响时间包含夜间空档

**输入:**
```json
{
  "first_response_times": [3, 5, 8, 12, 3600, 7200, 14400],
  "frt_extreme_sec": 1800
}
```

**期望输出:**
```json
{
  "raw_avg": 3604,
  "trimmed_avg": 7.0,
  "median": 12,
  "extreme_count": 3,
  "extreme_ratio": 0.43,
  "step_4_conclusion": "夜间排班缺口"
}
```

**断言:**
- `output.trimmed_avg != output.raw_avg`
- `output.extreme_ratio > 0.1`
```

#### 场景五：反例场景

把反例部分定义的误判场景也写成测试用例，确保 Skill 不会犯已知错误。

```markdown
### 反例验证_标签误标不应被信任

**输入:**
```json
{
  "label_top_triggers": ["好的", "你好", "？", "是的", "链接"],
  "label_name": "反馈产品外观脏污异物",
  "label_invalid_ratio": 0.3
}
```

**期望输出:**
```json
{
  "label_valid": false,
  "generic_word_ratio": 1.0,
  "fallback_mode": "keyword_statistics"
}
```

**断言:**
- `output.label_valid == false`
- `output.generic_word_ratio > label_invalid_ratio`
```

### 1.4 测试用例命名规范

命名格式：`{场景类型}_{具体描述}`

| 场景类型 | 示例 |
|---------|------|
| 正常_ | 正常_全量数据完整 |
| 边界_ | 边界_投诉率恰好5% |
| 异常_ | 异常_数据源不可访问 |
| 极端_ | 极端_首响包含夜间空档 |
| 反例_ | 反例_标签误标不应被信任 |

## 2. 反例库构建方法

### 2.1 反例的价值

反例（antipatterns）是 Skill 区别于简单规则引擎的关键特性。它告诉 AI Agent 「什么情况下看起来应该走某个分支，实际上不应该」。没有反例的 Skill 容易产生误判。

lint 规则 `check_test_coverage.antipatterns` 会检查是否定义了反例。建议每个生产级 Skill 至少包含 2-3 个反例。

### 2.2 反例的三个来源

#### 来源一：历史事故

从过去的误判事件中提取。这是最有价值的反例来源。

下面全部采用合成案例，不引用未随公开包提供的业务验证记录。

```markdown
1. **误判场景**：20 条合成消息中，16 条被错误规则打上“商品缺陷”标签。
   **正确做法**：核对规则和消息内容，不把标签覆盖比例直接当作真实缺陷比例。
   来源：本文构造的标签误触发示例。

2. **误判场景**：20 条合成首响记录中，19 条为 10 秒、1 条为 4610 秒；均值为 240 秒。
   **正确做法**：分别报告全量和分组结果，再核对长等待的原因与排班规则。
   若预先约定的有效口径允许排除该条，剩余均值为 10 秒；不得为改善指标任意删掉异常值。
   来源：本文构造的响应时长示例，不是实际企业服务指标。
```

#### 来源二：业务域知识

业务专家提出口径假设，再用数据确认。例如，一个合成报表的“自营收入 100”可能包含在“全渠道收入 160”中，不能直接相加。将范围、单位和去重规则写入测试，不能只写经验判断。

#### 来源三：技术陷阱

合成接口可同时返回 `labelList`（标签字典）与 `matchedLabels`（单条记录实际命中）。用接口合同和 fixture 核实字段含义，不把字典项数当作投诉次数。

### 2.3 反例编写模板

每个反例必须包含三个要素：

```markdown
N. **误判场景**: [用一句话描述「看起来像什么」]
   **正确做法**: [用一句话描述「实际应该怎么处理」+「为什么」]
   来源: [来源标识，便于追溯]
```

**常见问题：**
- 只写了场景没写原因 — 别人不知道为什么是误判
- 正确做法太笼统（「需要人工判断」）— 没有可操作性
- 没有来源 — 时间久了不知道这个反例是否还有效

### 2.4 反例的维护

反例应该持续积累，不应删除。当某个反例已经通过参数或逻辑调整被根治后，可以标记来源为「已修复 — 保留作为历史参考」。

## 3. Skill 质量评估标准

### 3.1 健康评分体系

SkillForge 的健康评分 (`/api/skills/{id}/health-score`) 从五个维度评估 Skill 质量：

| 维度 | 权重 | 满分条件 | 含义 |
|------|------|---------|------|
| 采纳率 | 30% | 近30天建议被采纳 >= 80% | 输出的建议是否被业务方接受 |
| 成功率 | 25% | 执行成功率 >= 95% | 运行时是否稳定 |
| 测试覆盖 | 20% | 测试用例数 >= 分支数 且 有反例 | 验证是否充分 |
| 新鲜度 | 15% | 最近30天内有更新 | 是否持续维护 |
| 数据健康 | 10% | 数据源可用 且 无漂移 | 依赖的数据是否正常 |

**评级标准：**

| 分数 | 等级 | 说明 |
|------|------|------|
| 90-100 | A | 优秀，可作为范例 |
| 75-89 | B | 良好，可生产使用 |
| 60-74 | C | 合格，建议改进 |
| 40-59 | D | 欠佳，需要重点关注 |
| 0-39 | F | 不合格，不建议生产使用 |

### 3.2 发布就绪检查

在发布前，SkillForge 会运行完整的质量门禁 (`/api/skills/{id}/publish-readiness`)：

1. **Lint 检查** — 8 项静态规则（元信息、分支完备性、不可达分支、阈值冲突、阈值空洞、术语一致性、测试覆盖、参数使用）
2. **AI 验证** — 用 LLM 模拟执行测试用例，检查逻辑一致性
3. **历史回放** — 检查最近的执行样本数量和采纳率
4. **跨 Skill 冲突** — 检查是否与同部门其他 Skill 的规则冲突

**阻断条件（必须修复才能发布）：**
- Lint 有 error 级别的问题
- 没有任何测试用例
- 元信息缺少 name 或 description

**警告条件（可发布但建议修复）：**
- 缺少兜底分支
- 测试覆盖不足
- 没有反例
- 有 magic number 未参数化

### 3.3 生产级 Skill 自查清单

发布前用以下清单自查：

**元数据（frontmatter）：**
- [ ] name 命名清晰，遵循 `{领域}-{功能}` 格式
- [ ] description 包含触发条件和适用范围
- [ ] department 正确设置
- [ ] trigger_type 正确（manual/cron/webhook/event）
- [ ] risk_level 正确评估
- [ ] params 中所有阈值都有 description 和 default

**目的（purpose）：**
- [ ] 20字符以上，说清解决什么业务问题
- [ ] 不只是重复 description

**决策步骤（steps）：**
- [ ] 每个步骤有明确的名称
- [ ] 每个步骤至少2个分支
- [ ] 每个步骤有兜底分支（else/其他情况）
- [ ] 阈值从大到小排列，无重叠无空洞
- [ ] 没有不可达分支
- [ ] 没有环引用
- [ ] Step 总数不超过7个
- [ ] 第一步检查数据质量/完整性

**测试用例（test_cases）：**
- [ ] 测试用例数 >= 分支数
- [ ] 覆盖正常路径、边界值、异常输入
- [ ] 输入和期望输出都是有效的 JSON
- [ ] 有断言规则

**反例（antipatterns）：**
- [ ] 至少2-3个反例
- [ ] 每个反例有场景、正确做法、来源
- [ ] 包含真实发生过的误判案例

**输出定义（output）：**
- [ ] 每个输出有明确的接收人
- [ ] 审批级别与 risk_level 一致
- [ ] 输出格式适合接收人（人看 card/text，机器消费 json）

**数据输入（data_inputs）：**
- [ ] 列出所有数据依赖
- [ ] 标注数据来源和刷新频率
- [ ] 考虑了数据延迟（T+1）

## 4. 常见错误和解决方案

### 4.1 决策逻辑类

#### 错误一：缺少兜底分支

这是 **最常见** 的问题（基线53%缺失率）。

```markdown
# 错误
  ├─ ROI > 1.5 → 加预算
  └─ ROI < 0.8 → 减预算
  # ROI在0.8-1.5之间呢？

# 修复
  ├─ ROI > 1.5 → 加预算
  ├─ ROI < 0.8 → 减预算
  └─ 其他情况 → 维持现状，持续观察
```

#### 错误二：均值陷阱

只看平均值做判断，被极端值误导。

```markdown
# 错误 — 直接用均值
### Step: 评估首响时间
  ├─ 平均首响 < 60s → 合格
  └─ 平均首响 >= 60s → 不合格

# 修复 — 先剔除极端值，看中位数和分布
### Step: 评估首响时间
  ├─ 剔除极端值(>{frt_extreme_sec}s)后，有效均值 <= {frt_warning_sec}s 且 中位数 <= 10s → 合格
  ├─ 有效均值 > {frt_warning_sec}s 或 中位数 > 30s → 需改善
  └─ 极端值占比 > 10% → 排班缺口（非个人问题）
```

#### 错误三：只有一个分支

一个步骤只有一个分支，意味着它不是一个决策点，只是一个执行步骤。

```markdown
# 错误 — 这不是决策，是执行
### Step 1: 拉取数据
  └─ 拉取数据

# 修复 — 加上失败分支，变成真正的决策
### Step 1: 拉取数据
  ├─ 数据源可访问 且 数据非空 → 拉取成功
      → 进入 Step 2
  └─ 数据源不可访问 或 返回为空 → 拉取失败
      动作: 尝试备用数据源 或 告警
```

#### 错误四：数据口径混用

不同数据源的统计口径不同，直接混用导致错误结论。

```markdown
# 错误 — 混用了品牌渠道数据和分销数据
品牌渠道日销354万 + 分销日销260万 = 总销614万 ← 错误！

# 原因
品牌渠道仅含三自有品牌（谜姬/霏慕/安可尼），分销含全品牌（包括代理品牌）。
它们有重叠部分，不能简单相加。

# 修复 — 在Skill中明确标注数据口径
## 已知数据陷阱

1. **口径差异**：品牌渠道（三自有）与分销（全品牌）不能混用。
   需要「全品牌全渠道」数据时用分销总览。
```

### 4.2 测试类

#### 错误五：测试用例只有正向路径

```markdown
# 错误 — 只测了"一切正常"的情况
### 正常场景
输入: {"data": "完整有效的数据"}
期望: {"status": "success"}

# 修复 — 补充异常和边界
### 正常场景
...

### 数据缺失场景
输入: {"data": null}
期望: {"status": "error", "message": "数据缺失"}

### 边界值场景
输入: {"roi": 1.2}  # 恰好在阈值上
期望: {"level": "yellow"}  # 明确边界归属
```

#### 错误六：期望输出太模糊

```markdown
# 错误 — 期望输出是一个模糊描述
期望: {"expected_keywords": ["日报", "成功"]}

# 修复 — 期望输出是精确的结构
期望: {
  "status": "success",
  "report_type": "daily",
  "cards_rendered": 6,
  "push_target": "销售运营群"
}
```

### 4.3 参数类

#### 错误七：参数没有 description

```yaml
# 错误
params:
  threshold:
    type: number
    default: 5.0

# 修复
params:
  complaint_alert_threshold:
    type: number
    description: "任意投诉类别占总会话百分比超过此值时触发告警建议"
    default: 5.0
```

#### 错误八：参数名不体现含义

```yaml
# 错误
params:
  t1: {type: number, default: 60}
  t2: {type: number, default: 1800}

# 修复
params:
  frt_warning_sec: {type: number, default: 60, description: "首响警戒线（秒）"}
  frt_extreme_sec: {type: number, default: 1800, description: "极端首响线（秒）"}
```

### 4.4 架构类

#### 错误九：Skill 太大（做了太多事）

**信号：** Step 超过 7 个、description 需要用「并且」连接多个功能、不同部门关心同一个 Skill 的不同部分。

**解决方案：** 拆分成多个 Skill，用 Playbook 编排。

#### 错误十：没有考虑数据延迟

```markdown
# 错误 — 直接分析当天数据
target_date 默认今天 → 但 avgResTime 等字段 T+1 才写入

# 修复 — 在已知陷阱中标注
## 已知数据陷阱
- 当天数据不完整：avgResTime、resWord 等字段 T+1 才写入，
  当天拉取会缺失。必须分析 T+1 及以前的数据。
```

## 5. 持续优化方法论

### 5.1 优化循环

Skill 不是写完就结束的。生产级 Skill 需要持续优化，遵循 PDCA 循环：

```
Plan（规划）→ Do（执行）→ Check（检查）→ Act（改进）
     ↑                                          |
     └──────────────────────────────────────────┘
```

**周期建议：**
- 每周：检查执行日志，发现新的误判场景
- 每月：回顾健康评分，更新反例库
- 每季度：检查参数是否需要调整，业务规则是否有变

### 5.2 从执行日志中发现问题

SkillForge 记录每次执行的 decision_log，包含走了哪个分支、用了什么参数值、最终结论是什么。通过分析执行日志可以发现：

**信号一：某个分支从来没被触发过**
- 可能：阈值设置不合理（太高或太低）
- 行动：检查该分支的条件是否合理，参数是否需要调整

**信号二：采纳率下降**
- 可能：业务环境变化导致规则不再适用
- 行动：与业务方沟通，更新决策逻辑

**信号三：频繁走兜底分支**
- 可能：主要条件没有覆盖常见情况
- 行动：分析兜底分支的输入数据，提取新的条件分支

### 5.3 参数调优

使用 SkillForge 的参数调优工具 (`/api/skills/{id}/param-tune`)：

1. 确定要优化的参数和候选值
2. 用历史数据做网格搜索
3. 对比不同参数组合的效果
4. 选择最优组合，更新 policy_pack

**示例：** 调优投诉告警阈值

```json
{
  "params": [
    {"name": "complaint_alert_threshold", "values": [3.0, 5.0, 7.0, 10.0]},
    {"name": "frt_warning_sec", "values": [30, 60, 90, 120]}
  ],
  "days": 30
}
```

### 5.4 反例驱动的改进

每次发现误判，按以下流程转化为改进：

```
发现误判 → 记录为反例 → 分析根因 → 选择修复方式：
  ├─ 调参数可修复 → 更新 policy_pack
  ├─ 需要新分支 → 修改决策树
  ├─ 需要新的数据验证 → 增加预处理步骤
  └─ 不可程序化修复 → 保留反例，依赖 Agent 学习
```

### 5.5 漂移检测

业务环境会变化，原来合理的阈值可能不再适用。SkillForge 的漂移检测 (`/api/skills/{id}/drift-check`) 会自动发现：

- **数据漂移：** 输入数据的分布发生显著变化
- **概念漂移：** 同样的输入开始产生不同的最优决策
- **性能漂移：** 采纳率持续下降

当检测到漂移时，应该重新评估参数和决策逻辑。

### 5.6 Skill 生命周期管理

| 阶段 | 状态 | 动作 |
|------|------|------|
| 草稿 | draft | 编写 Skill，通过 lint 检查 |
| 影子运行 | shadow | 在生产环境运行但不发送输出，对比人工决策 |
| 试运行 | active | 小范围使用，收集反馈 |
| 全量 | active | 正式生产使用 |
| 衰退 | active | 采纳率下降，需要优化 |
| 归档 | archived | 不再使用，保留历史记录 |

**影子运行是最关键的阶段。** 在影子运行中，Skill 的输出不会真正发送，而是与人工决策做对比。如果分歧率低于 5%，说明 Skill 质量足够投产。
