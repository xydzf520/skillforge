## 1. Skill 架构设计原则

### 1.1 一个 Skill 只解决一个业务决策

**核心原则：** 每个 Skill 应该聚焦于一个明确的业务判断点。如果你发现自己在一个 Skill 里处理多个不相关的决策，那应该拆成多个 Skill，用 Playbook 编排。

**判断标准：**
- 能用一句话说清楚这个 Skill 做什么决定 --> 粒度合适
- 描述需要用「并且」「同时还要」连接多个功能 --> 需要拆分
- 不同部门的人关心同一个 Skill 的不同部分 --> 需要拆分

**合成示例：** `support-quality-example` 可以包含标签验证、投诉识别与首响分析，但应围绕「判断客服数据质量和服务水平」这个核心目标；是否合并为一个 Skill，仍需根据职责、权限和验收边界判断。

**反面案例：** 把「ROI 评估」和「创意素材审核」放在同一个 Skill 里就不合理，因为它们是两个独立的判断过程，由不同岗位的人关心。

### 1.2 结构分层：从数据到决策到行动

一个生产级 Skill 应该包含 **六个完整层次**，每层缺一不可：

```
层次 1: 元数据（frontmatter）     — 谁负责、什么时候跑、风险多大
层次 2: 目的（purpose）          — 解决什么业务问题
层次 3: 数据输入（data_inputs）   — 需要什么数据、从哪来
层次 4: 执行步骤（steps）         — 如何做判断
层次 5: 输出定义（output）        — 结果发给谁、什么格式
层次 6: 质量保障（test_cases + antipatterns） — 怎么验证正确性
```

### 1.3 描述（description）的写法

description 是 AI Agent 判断是否触发该 Skill 的关键依据。好的 description 需要覆盖三个维度：

```yaml
# 差的写法 — 太笼统，Agent 不知道什么时候该用
description: 销售数据分析

# 好的写法 — 说清了「什么场景触发」+「能做什么」+「不能做什么」
description: >
  直接调用 bi.example.com API 查询示例企业App用户数据，无需浏览器点击。
  仅用于App数据查询，销售/业绩数据统一使用 maxcompute 数仓。
  当用户查询App用户数据（DAU/新增/留存/性别/设备分布）时自动调用。
```

description 公式：**「做什么」+「适用场景」+「不适用场景」**

### 1.4 风险等级定义

风险等级决定了审批流程和告警策略。选择时看「最坏情况下的业务影响」：

| 等级 | 定义 | 典型场景 | 审批要求 |
|------|------|---------|---------|
| R1 | 只读/可逆 | 数据查询、报表生成 | 无需审批 |
| R2 | 对外发送/低风险写入 | 钉钉日报推送、内部告警 | 部门主管 |
| R3 | 不可逆操作/涉及外部系统 | 文档抽取推送业务系统、批量修改 | 部门主管 + AI 负责人 |
| R4 | 涉及资金/高敏感 | 预算调整建议、投放决策 | 多级审批 |

**常见错误：** 把「钉钉日报推送」标为 R1。虽然日报本身是只读数据的展示，但「对外发送消息」是一个不可撤回的动作，应该是 R2。

### 1.5 Skill 目录结构

每个 Skill 在 skills-repo 中是一个独立目录，标准结构如下：

```
my-skill/
  SKILL.md           # 核心文件：决策逻辑、参数、测试
  SKILL.hermes.md    # （可选）Hermes 运行时格式，由系统自动生成
  intent.md          # （可选）需求意图文档
  references/        # （可选）参考文档
    api.md           #   外部 API 文档
    changelog.md     #   变更记录
  scripts/           # （可选）辅助脚本
  policy_pack.yaml   # （可选）参数策略包
```

## 2. 决策树设计模式

### 2.1 五大基本模式

SkillForge 的 motif 库识别了五种常见的决策模式。选择合适的模式是设计好 Skill 的基础。

#### 模式一：阶梯决策（Ladder Decision）

**适用场景：** 根据某个指标的数值区间给出不同等级的判定。最常见的模式。

**特征：** 同一步骤内 3+ 个分支，用阈值区分绿/黄/红三级。

```markdown
### Step 1: 投诉率判定

  ├─ 任意投诉类别占总会话 >= 5% → 红灯：投诉率异常
      动作: 高亮该类别，建议排查具体问题商品/批次/流程
  ├─ 投诉类别占比 1%~5% → 黄灯：投诉需关注
      动作: 记录但不告警，持续观察趋势
  └─ 所有投诉类别占比 < 1% → 绿灯：投诉率正常
      动作: 不需额外动作
```

**关键要点：**
- 阈值从大到小排列（先判断最严重的情况）
- 最后一个分支必须是兜底（覆盖所有剩余情况）
- 每个等级的「结论」和「动作」都要明确

#### 模式二：阶段流程（Stage Flow）

**适用场景：** 需要按顺序执行多个步骤，前一步的输出是后一步的输入。

**特征：** 3+ 步骤，每步 1-2 个分支，通过 next_step 串联。

```markdown
### Step 1: 数据质量检查

  ├─ 有效会话占比 >= 50% → 数据可用
      动作: 进入标签验证
      → 进入 Step 2
  └─ 有效会话占比 < 50% → 数据质量差
      动作: 报告异常，停止深度分析

### Step 2: 标签有效性验证

  ├─ 标签触发内容与语义一致 → 标签有效
      动作: 可直接使用标签数据
      → 进入 Step 3
  └─ 通用词占比 > 30% → 标签配置有误
      动作: 切换到关键词统计模式
      → 进入 Step 3

### Step 3: 业务分析
...
```

**关键要点：**
- 每个步骤有明确的「通过」和「失败」出口
- 失败时要有明确的止损动作（不是简单地「终止」）
- 合成的 `support-quality-example` 可用 5 步阶梯式分析说明这种模式

#### 模式三：边界保护（Boundary Protection）

**适用场景：** 需要识别极端值或异常情况，交给人工处理。

**特征：** 有明确的「安全阈值」，超出时走人工复核。

```markdown
### Step 1: 边界检查

  ├─ 金额 > 50万 → 超出自动处理上限
      动作: 转人工审批，标记高优先级
  ├─ 金额 < 0 → 数据异常
      动作: 标记数据错误，通知数据团队
  └─ 其他情况 → 在安全范围内
      动作: 继续自动处理
      → 进入 Step 2
```

**关键要点：**
- 极端值检查必须在业务逻辑之前
- 人工复核的通知路径要明确（通知谁、用什么渠道）
- 不要用「终止」代替人工复核 — 业务不能因为一个异常值就停摆

#### 模式四：数据兜底（Data Fallback）

**适用场景：** 数据源可能缺失、不完整或延迟。

**特征：** 有分支专门处理数据缺失的情况。

```markdown
### Step 1: 检查数据完整性

  ├─ 数据源可访问 且 当天数据完整 → 数据就绪
      动作: 进入分析
      → 进入 Step 2
  ├─ 数据缺失 < 3 天 → 数据不完整但可用
      动作: 使用历史数据回退，在结果中标注"样本不足"
      → 进入 Step 2
  └─ 数据源不可访问 或 全部缺失 → 无法分析
      动作: 暂停并告警SRE，写入告警暂停状态
```

**关键要点：**
- 数据兜底是生产级 Skill 必须有的 — 数据源100%可靠在现实中不存在
- 区分「降级可用」和「完全不可用」两种情况
- bi-query 中的「API全空 → 浏览器兜底 → 仍无数据才放弃」就是三路降级的优秀案例

#### 模式五：冲突消解（Conflict Resolution）

**适用场景：** 多个规则可能同时命中，需要确定优先级。

**特征：** 有明确的优先级排序，通过 next_step 编排处理顺序。

```markdown
### Step 1: 优先级判定

  ├─ 存在安全合规问题 → 立即阻断
      动作: 直接终止，不执行后续任何步骤
  ├─ 存在财务风险 → 需审批
      动作: 挂起，通知财务审批人
  └─ 仅业务建议 → 正常执行
      动作: 按标准流程处理
      → 进入 Step 2
```

### 2.2 模式组合

复杂 Skill 可以组合多种模式。合成的 `support-quality-example` 可组合：

1. **阶段流程**（Step 1 → Step 2 → Step 3 → Step 4 → Step 5）
2. **数据兜底**（Step 1 检查数据质量）
3. **阶梯决策**（Step 3 投诉率三级判定、Step 4 首响三级判定）
4. **边界保护**（Step 4 极端值剔除）

推荐的组合顺序：**数据兜底 → 边界保护 → 阶梯决策 → 冲突消解 → 输出**

### 2.3 决策树设计的铁律

**铁律一：每个步骤必须有兜底分支**

SkillForge 的 lint 规则 `check_branch_completeness` 会自动检查这一点。基线数据显示 **53% 的 Skill 缺少兜底分支**，这是最常见的质量问题。

```markdown
# 错误 — 如果 ROI 恰好等于 1.2 会怎样？
  ├─ ROI > 1.2 → 绿灯
  └─ ROI < 0.8 → 红灯

# 正确 — 用「其他情况」覆盖所有未命中的 case
  ├─ ROI > 1.2 → 绿灯
  ├─ ROI < 0.8 → 红灯
  └─ 其他情况 → 黄灯（人工评估）
```

**铁律二：阈值排列有序，不能重叠**

lint 规则 `check_threshold_conflict` 检查阈值重叠，`check_threshold_gap` 检查阈值空洞。

```markdown
# 错误 — ROI=1.6 同时满足两个条件
  ├─ ROI > 1.2 → 黄灯
  ├─ ROI > 1.5 → 绿灯

# 正确 — 大阈值在前
  ├─ ROI > 1.5 → 绿灯
  ├─ ROI > 1.2 → 黄灯
  └─ 其他情况 → 红灯
```

**铁律三：不能有不可达分支**

lint 规则 `check_unreachable_branch` 检查。兜底分支后面不能再有其他分支。

```markdown
# 错误 — "备用方案"永远不会执行
  ├─ ROI > 1.5 → 绿灯
  ├─ 其他情况 → 黄灯
  └─ ROI < 0.5 → 备用方案     ← 不可达！

# 正确 — 兜底放最后
  ├─ ROI > 1.5 → 绿灯
  ├─ ROI < 0.5 → 红灯
  └─ 其他情况 → 黄灯
```

**铁律四：不能有环引用**

Step A → Step B → Step A 会导致无限循环。validation_service 会做环检测。

**铁律五：Step 不超过 7 个**

认知科学表明人类短时记忆上限是 7 个元素。超过 7 个 Step 的 Skill 意味着它需要拆分。

## 3. 参数设计指南

### 3.1 什么应该做成参数

**做成参数的信号：**
- 阈值类数字：投诉率告警线、首响警戒线、ROI 及格线
- 可能因业务变化而调整的值：时间窗口、样本最低数量
- 不同部门/场景需要不同取值的配置

**不应该做成参数的信号：**
- 逻辑结构（「先检查数据质量再分析」不应该是参数）
- 固定的枚举值（「红/黄/绿」三级不需要参数化）
- 安全边界（最大重试次数等系统参数由平台控制）

### 3.2 参数定义规范

每个参数必须包含四个要素：类型、描述、默认值、影响范围。

```yaml
params:
  # --- 完整的参数定义 ---
  complaint_alert_threshold:
    type: number
    description: "任意投诉类别占总会话百分比超过此值时触发告警建议"
    default: 5.0
    # 在 SKILL.md 正文中说明影响范围

  # --- 最小但完整的参数定义 ---
  frt_warning_sec:
    type: number
    description: "首响时间超过此秒数视为异常"
    default: 60
```

### 3.3 参数命名规范

| 规则 | 正确 | 错误 |
|------|------|------|
| 用英文下划线命名 | `complaint_alert_threshold` | `投诉告警线` |
| 名称体现含义 | `frt_warning_sec` | `threshold_1` |
| 带单位后缀 | `frt_extreme_sec` | `frt_extreme` |
| 布尔值用 `is_`/`enable_` 前缀 | `enable_fallback` | `fallback` |
| 比率用 `_ratio` 或 `_pct` 后缀 | `label_invalid_ratio` | `label_invalid` |

### 3.4 参数影响文档化

例如，用表格明确 `support-quality-example` 中每个参数影响哪个决策步骤：

```markdown
## 参数影响

| 参数 | 影响的决策步骤 | 影响说明 |
|------|---------------|---------|
| `complaint_alert_threshold` | step_3 | 越低越敏感。默认5%表示每20条对话里有1条投诉就告警 |
| `frt_warning_sec` | step_4 | 首响警戒线。默认60s，调低则更严格 |
| `frt_extreme_sec` | step_4 | 极端值剔除线。默认1800s。调低会误判晚班客服 |
```

**要点：不仅说明参数做什么，还要说明调大/调小的后果。** 这让业务方不需要理解技术细节就能合理调参。

### 3.5 参数调优工具

SkillForge 提供了参数调优接口 (`/api/skills/{id}/param-tune`)，支持网格搜索最优参数组合。设计参数时要考虑可调性：

- 合理的调整粒度（投诉阈值以 1% 为步长，不是 0.001%）
- 合理的调整区间（首响警戒线 10s ~ 300s，不是 0 ~ 86400s）
- 调整后的可观测性（参数变化应该能在执行日志中体现）

### 3.6 避免 Magic Number

lint 规则 `check_param_usage` 会检测条件中的硬编码数值。超过 3 个 magic number 就会提示你抽取参数。

```markdown
# 差 — 1.2、0.8、50000 是哪来的？
  ├─ ROI > 1.2 → 绿灯
  ├─ ROI < 0.8 → 红灯
  ├─ 消耗 > 50000 → 需审批

# 好 — 用参数引用，可在 policy_pack 中配置
  ├─ ROI > {roi_green_threshold} → 绿灯
  ├─ ROI < {roi_red_threshold} → 红灯
  ├─ 消耗 > {cost_approval_limit} → 需审批
```

## 6. 输出定义最佳实践

### 6.1 输出表格的四列含义

```markdown
## 输出

| 输出项 | 格式 | 接收人 | 审批级别 |
|---|---|---|---|
| 日报卡片 | dingtalk_card | 销售运营群 | R2 |
| 分析报告 | json | AI工作流引擎 | 自动 |
| 异常告警 | text | SRE值班群 | R1 |
```

| 列 | 含义 | 常用值 |
|---|---|---|
| 输出项 | 产出物名称 | 日报、告警、报告、推荐列表 |
| 格式 | 数据格式 | text / json / dingtalk_card / markdown / csv |
| 接收人 | 谁消费这个输出 | 具体钉钉群 / 业务系统 / 下游Skill / 终端用户 |
| 审批级别 | 是否需要人工确认 | R1/R2/R3/R4 / 自动 |

### 6.2 输出设计原则

**原则一：输出必须驱动行动**

差的输出：「ROI为1.3」— 然后呢？

好的输出：「ROI 1.3 > 及格线1.2，建议维持当前预算，可小幅加码10%测试」— 接收人知道该做什么。

**原则二：附带原始数据**

参考 bi-query 的铁律4：「总结类输出必须附带原始数据」。这让接收人可以验证结论是否正确。

**原则三：说清逻辑链路**

参考 bi-query 的铁律5：在输出末尾用一句话描述数据从哪来、经过什么处理、为什么得出这个结论。

```markdown
> 逻辑：品牌中心日报「每日趋势」→ API取值 → 交叉验证 → 7日均值比对 → 超阈值触发预警。
```

**原则四：区分机器消费和人类消费**

如果输出是给下游系统消费的，用 JSON 格式并定义清晰的字段。如果输出是给人看的，用 text 或 dingtalk_card 格式。

### 6.3 输出契约文档化

对于复杂输出，应定义完整的输出契约，列出每个字段的类型、含义与来源。下面是合成示例：

```markdown
## 输出契约

```json
{
  "total": 12000,
  "valid": 9360,
  "real_complaints": {
    "质量问题": 180,
    "退款退货": 420
  }
}
```

### 字段说明

| 字段 | 类型 | 含义 | 来源 |
|------|------|------|------|
| total | integer | 原始总会话数（含无效） | len(records) |
| valid | integer | 有效会话数 | 过滤后计数 |
| real_complaints | object | 各类投诉的独立会话数 | 关键词验证，会话级去重 |
```
