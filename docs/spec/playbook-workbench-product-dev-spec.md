## 1. 背景与问题定义

### 1.1 当前现状

当前 Playbook 相关能力被拆成 3 个独立页面：

| 页面 | 路由 | 主要职责 | 当前问题 |
|------|------|----------|----------|
| Playbook 查看页 | `/playbook/:name` | 查看流程、审核、执行入口 | 只有只读画布 + Mermaid + 基本信息，普通用户不知道下一步做什么 |
| Playbook 编辑页 | `/playbook/:name/edit` | 编辑流程、保存、验证 | 只有画布 + YAML，缺少背景信息、审核状态、执行上下文 |
| Playbook 实时执行页 | `/playbook/:name/live` | 运行中状态与日志 | 和详情页割裂，用户执行后还要跳页理解 run_id |

### 1.2 代码层面的实际拆分

当前拆分不是抽象设计，而是实现层硬切：

- 查看页固定使用只读 iframe：
  - `web/src/pages/playbook/PlaybookView.vue`
- 编辑页使用可编辑 iframe，并外挂 YAML 和条件编辑器：
  - `web/src/pages/playbook/PlaybookEdit.vue`
- 实时页再单独嵌一个 `live=1` iframe：
  - `web/src/pages/playbook/PlaybookLive.vue`
- `playbook-editor` 子应用内部按 URL 参数切换 `readonly / live / edit` 三种模式：
  - `playbook-editor/src/App.tsx`

这种拆法的结果是：能力不是没有，而是被分散到不同页面和不同心智模型里。

### 1.3 当前体验的核心问题

#### P1. 普通用户看不懂

- 查看页默认出现“Mermaid 流程图”“只读拓扑”等偏工程化概念。
- 用户首先关心的是：
  - 这个流程是干什么的
  - 现在能不能用
  - 有问题没有
  - 我要改哪里
  - 我点哪个按钮是下一步
- 当前页面没有给出清晰答案。

#### P2. 页面是按技术实现拆的，不是按用户任务组织的

用户真实任务是：

1. 看懂流程
2. 改流程
3. 检查问题
4. 保存
5. 提交审核
6. 运行并看结果

当前产品却要求用户记住：

1. 查看页
2. 编辑页
3. 实时页
4. Mermaid 视图
5. YAML 预览

这不符合普通人操作顺序。

#### P3. 上下文不断丢失

- 从查看到编辑要跳页
- 从编辑到运行要再切上下文
- 从运行到监控还要再去 live 页
- 审核信息只在查看页顶部，编辑页没有同等上下文

#### P4. “高级信息”压过了“主任务信息”

默认展示 Mermaid 和 YAML 这类高级信息，会让用户误以为这是一个技术工具，而不是业务流程工作台。

#### P5. 现有能力没有串成闭环

后端已经具备以下能力：

- 读取流程
- 保存流程
- 校验流程
- 提交流程审核
- 执行流程
- 返回 `run_id`
- WebSocket 实时推送运行状态

问题不是能力缺失，而是产品编排没有把这些能力组织成“一个页面内的一条工作链”。

## 2. 目标用户与核心任务

### 2.1 主要用户

| 角色 | 典型身份 | 核心诉求 |
|------|----------|----------|
| 流程编辑者 | AI 工程师 / AIBP / 运营中台 | 低成本看懂、修改、检查、保存流程 |
| 流程审核者 | 审批人 / 部门负责人 | 看清本次变更、流程逻辑和风险，快速通过或驳回 |
| 流程使用者 | 业务同学 / 非技术同学 | 看懂流程用途、步骤、分支和最近运行情况 |
| 流程运维者 | 平台管理员 / 研发 | 看执行状态、失败位置、日志、回放线索 |

### 2.2 设计时默认面对的用户

本方案默认首先服务“懂业务但不一定懂 Mermaid / YAML / React Flow”的用户。

产品默认视角应满足：

- 第一次进入页面的人能知道这是做什么的
- 不看文档也能找到“下一步”
- 80% 常用操作不需要理解技术术语

### 2.3 统一后的核心任务

统一工作台要支持用户在一个页面连续完成以下任务：

1. 浏览流程
2. 查看步骤和分支
3. 进入编辑
4. 修改节点、连线和条件
5. 检查当前草稿问题
6. 保存
7. 提交审核
8. 执行流程
9. 观察实时运行
10. 查看结果或失败原因

## 3. 产品目标与非目标

### 3.1 产品目标

| 目标 | 说明 | 衡量标准 |
|------|------|----------|
| 单页闭环 | 查看、编辑、校验、审核、执行、监控尽量在同一工作台完成 | 主链路不再需要跨 3 个页面 |
| 普通人可理解 | 默认文案和结构偏业务表达，不强推技术概念 | 首次进入页面 30 秒内知道下一步 |
| 降低切换成本 | 不因为模式变化丢失流程上下文 | 详情、编辑、运行属于一个工作台心智 |
| 保留高级能力 | Mermaid、YAML、文本配置继续存在，但降级为高级信息 | 默认界面不被高级内容打扰 |
| 可渐进上线 | 基于现有 Vue 页面 + iframe editor + API 能力演进，不推倒重来 | Phase 1 可在当前架构上落地 |

### 3.2 非目标

- 不在本轮重写 `playbook-editor` 技术栈
- 不在本轮移除 iframe 嵌入架构
- 不在本轮重做 Playbook 列表页的 IA
- 不在本轮把 Mermaid 变成主要编辑方式
- 不在本轮引入复杂协同编辑能力

## 4. 核心设计原则

### 4.1 一个流程，一个工作台

用户不需要理解“查看页 / 编辑页 / 运行页”的拆分，用户只需要知道：

“我在这个流程的工作台里，可以看、改、查、提、跑。”

### 4.2 默认呈现业务意义，不默认呈现技术结构

默认应先展示：

- 流程用途
- 触发方式
- 步骤数量
- 当前状态
- 是否有问题
- 下一步动作

高级内容如 Mermaid、YAML、原始条件表达式，统一放到“高级”区域。

### 4.3 模式切换是轻量切换，不是跳世界

浏览、编辑、执行监控是同一工作台的不同模式或标签，而不是不同产品。

### 4.4 问题要可定位

“检查问题”不能只告诉用户有问题，还要能：

- 定位到具体步骤
- 高亮相关节点或连线
- 给出人能懂的提示

### 4.5 执行结果要回到流程图上

执行不是另一套世界。运行状态、步骤结果、失败位置要直接映射回流程图。

### 4.6 先保证能用，再增加高级性

优先把用户高频主链路打通，再谈更复杂的导出、历史 diff、批量操作等增强功能。

## 5. 目标信息架构

### 5.1 路由目标态

#### 主路由

- `GET /playbook/:name`
  - 唯一主工作台入口
  - 页面内承载浏览、编辑、审核、执行监控四种视角

#### 辅助兼容路由

- `/playbook/:name/edit`
  - 第一阶段可保留，重定向到 `/playbook/:name?mode=edit`
- `/playbook/:name/live`
  - 第一阶段可保留，重定向到 `/playbook/:name?tab=run&run_id=xxx`

### 5.2 页面内信息架构

工作台分为 5 个层级：

1. 顶部概览与主操作
2. 主画布区
3. 右侧上下文信息区
4. 下方高级信息区
5. 审核与运行状态覆盖层

### 5.3 主要标签页

建议工作台顶部使用一级标签或分段控制，统一 4 个主视角：

| 标签 | 默认用户看到什么 | 说明 |
|------|------------------|------|
| 总览 | 流程简介 + 只读流程图 + 步骤摘要 + 审核状态 | 默认打开 |
| 编辑流程 | 可编辑画布 + 右侧配置面板 + 检查问题 + 保存 | 编辑者主入口 |
| 执行监控 | 运行中流程图 + 步骤日志 + 当前 run 状态 | 运行时主入口 |
| 高级 | 文本流程图、原始配置、调试信息 | 技术用户使用 |

## 6. 统一工作台页面设计

### 6.1 页面总布局

推荐布局：

```text
┌─ 顶部概览栏 ──────────────────────────────────────────────────────────────┐
│ 返回 | 流程名称 | 状态标签 | 触发方式 | 步骤数 | 最近更新时间             │
│ 浏览 | 编辑流程 | 执行监控 | 高级      | 检查问题 | 保存 | 提交审核 | 开始执行 │
├───────────────┬───────────────────────────────────────────────┬──────────┤
│ 左/中主内容区 │                主流程图画布                    │ 右侧信息区 │
│               │                                               │          │
│               │ 浏览模式: 只读浏览                             │ 说明      │
│               │ 编辑模式: 可拖拽/可选中/可配置                 │ 步骤详情   │
│               │ 运行模式: 节点状态回写                         │ 问题清单   │
│               │                                               │ 分支条件   │
│               │                                               │ 运行结果   │
├───────────────┴───────────────────────────────────────────────┴──────────┤
│ 下方高级信息区：文本流程图 | 原始配置 | 变更信息 | 审核单 | 调试信息       │
└───────────────────────────────────────────────────────────────────────────┘
```

### 6.2 顶部概览栏

#### 展示信息

- 流程名称
- 流程一句话说明
- 所属部门
- 触发方式
- 步骤数
- SLA
- 当前状态
- 是否存在未保存修改
- 当前是否关联审核单
- 最近一次执行状态

#### 主按钮顺序

按钮必须遵循用户任务顺序：

1. `检查问题`
2. `保存`
3. `提交审核`
4. `开始执行`

不建议把“编辑”做成主要 CTA。页面本身就是工作台，模式切换即可。

### 6.3 总览模式

#### 目标

让第一次进入的人在 20-30 秒内理解：

- 这个流程做什么
- 主要经过哪些步骤
- 是否能执行
- 是否存在审核或问题

#### 默认内容

- 业务说明卡
- 流程图只读视图
- 步骤摘要列表
- 审核状态卡
- 最近一次执行摘要

#### 不默认展示

- Mermaid 原文
- YAML / JSON 原始配置
- 技术字段细节

### 6.4 编辑流程模式

#### 主区域

- 可编辑流程画布
- 左侧 Skill 资源与工具入口
- 右侧节点/连线配置区

#### 辅助区域

- 问题清单卡
- 变更摘要卡
- 未保存修改提示

#### 编辑模式要回答的三个问题

1. 我现在改的是哪里
2. 我改完有没有问题
3. 我下一步是保存、继续改，还是提交审核

### 6.5 执行监控模式

#### 目标

执行后用户不需要离开当前工作台，即可看到：

- 本次运行状态
- 哪个步骤在执行
- 哪个步骤失败
- 当前已经完成多少步骤
- 运行日志

#### 必须展示的信息

- 当前 `run_id`
- 总步骤数 / 已完成数
- 当前状态标签
- 实时节点高亮
- 步骤级日志时间线
- 失败步骤错误信息

#### 推荐增强

- 一键重新聚焦到正在执行的步骤
- 日志点击联动画布节点
- 失败后直接跳回编辑模式并定位节点

### 6.6 高级模式

#### 作用

容纳工程化信息，但不打扰普通用户。

#### 内容

- 文本流程图
- 原始配置
- Mermaid 代码或 SVG
- 调试字段
- 布局数据

#### 命名要求

不要把标签直接命名为 `Mermaid` 或 `YAML`。推荐：

- `文本流程图`
- `原始配置`
- `高级`

### 6.7 右侧信息区

右侧信息区按用户当前选中内容动态切换：

| 选中对象 | 右侧显示 |
|----------|----------|
| 无选中 | 流程说明、问题清单、步骤摘要 |
| 节点 | 节点名称、绑定 Skill、超时、失败策略、参数覆盖 |
| 连线 | 分支条件、来源步骤、目标步骤、条件说明 |
| 运行中节点 | 当前状态、开始时间、最近日志 |
| 失败节点 | 错误摘要、关联日志、建议动作 |

### 6.8 问题清单

问题清单是普通用户理解“哪里不对”的关键区域，必须具备：

- 严重级别
- 问题标题
- 人能看懂的说明
- 点击后定位节点

示例：

- `步骤 step_3 未配置 skill`
- `步骤 step_5 存在循环依赖`
- `分支 A→B 条件为空，可能导致误流转`

### 6.9 审核区

审核信息不应只存在于总览顶部。统一工作台中，审核必须常驻可见：

- 是否已提交审核
- 审核单编号
- 当前审核状态
- 审核人
- 差异摘要
- 通过 / 驳回动作

在编辑模式下，如果当前流程正在审核中，页面仍应明确提示，避免用户误以为没有审核上下文。

## 7. 关键用户流程

### 7.1 打开现有流程

1. 用户进入 `/playbook/:name`
2. 默认显示总览模式
3. 用户先看到流程用途、状态、步骤数、主流程图
4. 页面给出明显主动作：
   - `编辑流程`
   - `检查问题`
   - `开始执行`

### 7.2 修改流程

1. 点击 `编辑流程`
2. 进入可编辑画布
3. 用户拖拽、改节点、改连线、改条件
4. 右上角出现 `未保存修改`
5. 右侧问题清单实时更新

### 7.3 检查问题

#### 产品要求

- 检查的应该是“当前草稿”，不是“上一次已保存版本”
- 页面要区分：
  - `当前草稿检查结果`
  - `已保存版本检查结果`

#### 交互结果

- 无问题：提示 `检查通过，可保存或提交审核`
- 有问题：列表展示问题项，并允许定位

### 7.4 保存

1. 点击 `保存`
2. 持久化当前步骤和布局
3. `未保存修改` 消失
4. 页面显示 `已保存`
5. 如果之前已做草稿检查，保存后结果继续保留

### 7.5 提交审核

1. 若存在未保存修改，先提示 `请先保存再提交审核`
2. 提交前再次检查当前保存版本
3. 校验通过后创建审核单
4. 页面顶部进入 `待审核` 状态
5. 若当前用户具备审核权限，可直接进行通过/驳回

### 7.6 开始执行

1. 点击 `开始执行`
2. 弹出执行确认框
3. 可填写运行参数
4. 提交后获得 `run_id`
5. 页面自动切换到 `执行监控` 视角
6. 画布开始显示实时状态

### 7.7 查看失败并返回修改

1. 某步骤执行失败
2. 监控模式中高亮失败节点
3. 右侧展示失败摘要与日志
4. 用户点击 `去修改`
5. 页面切回编辑模式并定位到失败节点

## 8. 交互与文案规范

### 8.1 术语简化表

| 当前术语 | 面向用户的术语 | 说明 |
|----------|----------------|------|
| Mermaid | 文本流程图 | 技术术语降级 |
| YAML / JSON | 原始配置 | 统一成用户可理解概念 |
| Validate | 检查问题 | 避免技术化 |
| Publish | 提交审核 | 明确业务动作 |
| Run | 开始执行 | 更符合业务语义 |
| Condition | 分支条件 | 普通用户更容易理解 |
| Readonly Topology | 浏览模式 | 不直接暴露只读概念 |

### 8.2 空状态文案

#### 无步骤

- `这个流程还没有步骤。你可以从左侧拖入 Skill，或添加一个空节点。`

#### 无问题

- `当前没有发现结构问题。可以保存，或直接提交审核。`

#### 无运行记录

- `这个流程还没有最近执行记录。点击“开始执行”即可运行一次。`

### 8.3 条件编辑器表达方式

条件编辑器应尽量句子化，而不是暴露结构化 JSON：

- 如果【步骤 A 的结果】大于【80】则走【通过】
- 如果【步骤 B 的状态】等于【failed】则走【人工处理】

高级模式才允许查看结构化表达。

### 8.4 可见性规范

- 主流程动作必须位于首屏
- 高级信息不能抢主视觉
- 任何校验错误必须能定位
- 任何运行失败必须能回到对应节点

## 10. 后端与接口要求

### 10.1 可复用现有接口

当前后端已有接口足够支撑第一阶段：

| 接口 | 用途 |
|------|------|
| `GET /playbooks/{name}` | 加载流程详情 |
| `PUT /playbooks/{name}` | 保存流程 |
| `POST /playbooks/{name}/publish` | 提交审核 |
| `POST /playbooks/{name}/run` | 开始执行 |
| `GET /playbooks/{name}/mermaid` | 文本流程图 |
| `POST /playbooks/{name}/validate` | 校验已保存版本 |
| `POST /playbooks/validate` | 校验当前草稿 |
| `WS /api/playbooks/ws/playbook-live/{run_id}` | 运行实时事件 |

### 10.2 第一阶段必须调整的前端调用

#### 调整 1：草稿校验优先

当前编辑页只调用：

- `POST /playbooks/{name}/validate`

这会导致“检查问题”检查的是旧版本，不是当前画布草稿。

统一工作台必须增加：

- `playbookApi.validateDraft(data)` → `POST /playbooks/validate`

#### 调整 2：执行后自动进入监控

`POST /playbooks/{name}/run` 已返回 `run_id`，工作台应在返回成功后：

1. 保存 `run_id`
2. 切换到 `run` 模式
3. 建立 WebSocket 订阅

### 10.3 建议新增但非阻断接口

第二阶段可考虑新增：

| 接口 | 作用 | 优先级 |
|------|------|--------|
| `GET /playbooks/{name}/summary` | 统一返回概览信息、最近运行摘要、审核概览 | P2 |
| `GET /playbooks/{name}/runs/latest` | 获取最近一次运行简表 | P2 |
| `GET /playbooks/{name}/history` | 变更历史 | P3 |

### 10.4 审核信息复用

当前查看页已有审核加载逻辑，统一工作台需要保留并抽离，避免编辑模式丢失审核信息。

## 12. 边界情况与异常处理

### 12.1 存在未保存修改时离开页面

必须提示：

- `当前有未保存修改，离开后将丢失，是否继续？`

### 12.2 提交审核前有未保存修改

必须阻止直接提交审核，并提示：

- `请先保存当前修改，再提交审核。`

### 12.3 执行时存在未保存修改

提供两个选择：

- `执行已保存版本`
- `先保存再执行`

默认推荐：

- `先保存再执行`

### 12.4 草稿检查失败

必须同时给出：

- 总数
- 问题列表
- 节点定位

不能只弹一句 `验证失败`。

### 12.5 运行过程中 WebSocket 断开

页面应区分：

- 正在重连
- 已失去连接
- 已达到最大重试次数

并保留已有日志，不要因为断线清空上下文。

### 12.6 无 Mermaid / 文本流程图时

高级区显示：

- `当前流程暂无文本流程图。你仍可使用上方可视化流程图查看结构。`

### 12.7 无步骤时

编辑模式应直接引导：

- `从左侧拖入 Skill 开始搭建`
- `添加空节点`

## 13. 验收标准

### 13.1 产品验收

满足以下条件才算完成：

1. 用户进入 `/playbook/:name` 后，无需跳到 `/edit` 就能完成主要工作流
2. 总览、编辑、执行监控在同一页面中切换
3. “检查问题”检查的是当前草稿，不是旧保存版本
4. 执行后自动切到监控视角，并显示实时状态
5. Mermaid / 原始配置默认不抢主视觉
6. 审核信息在总览和编辑模式下都可见
7. 问题项和运行失败项都能定位到对应节点

### 13.2 研发验收

#### 前端

1. 新工作台页面可替代原查看页与编辑页主链路
2. iframe 在三种模式下行为正确
3. 页面刷新后工作台模式、当前 `run_id`、审核上下文可恢复
4. 旧路由可兼容跳转

#### 后端

1. 现有接口无需破坏性修改即可支持 Phase 1
2. 草稿校验接口被前端正式接入
3. 运行返回 `run_id` 后可直接用于监控

#### E2E

至少覆盖：

1. 打开流程工作台默认总览
2. 切换到编辑模式并修改节点
3. 进行草稿检查并显示问题
4. 保存后未保存状态消失
5. 提交审核并显示审核单
6. 执行后自动切换到监控模式
7. Mermaid / 原始配置仅在高级区出现

## 结论

Playbook 当前不是“功能不够”，而是“功能被拆散”。正确方向不是继续补零散页面，而是统一成一个流程工作台。

统一后的目标不是技术上更炫，而是让普通用户用一句话理解产品：

**“我在这个页面里，就能看懂流程、修改流程、检查问题、提交审核、开始执行、看执行结果。”**

这就是本方案的核心。
