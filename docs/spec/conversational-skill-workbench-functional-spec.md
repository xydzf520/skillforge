# 对话式 Skill 工作台功能定义

> **阅读范围**：本文保留原项目的设计与版本演进记录，不作为公开准备版的安装或验收指南。正文中的“当前／已完成／已上线”须结合当时版本理解；现行可用范围见[能力地图](../public/CAPABILITIES.md)，实测范围见[验证记录](../public/VALIDATION.md)。规范性权限与审核要求不因该说明而放宽。


> 日期：2026-04-05
> 配套方案：`docs/archive/conversational-skill-workbench-proposal.md`
> 目的：把“对话生成完整 Skill + 专业编排与深度调优”落成一份可执行的功能定义

## 1. 产品定义

这是一个 `双模式 Skill 工作台`：

- 小白模式：通过对话形成一个完整 Skill
- 专业模式：对 Skill 做结构化编辑、工作流编排和深度调优

它不是一个纯聊天产品，也不是一个纯编排工具。

它的核心价值是：

1. 让不会写 Skill 的用户也能做出一个可运行的完整 Skill
2. 让懂业务或懂系统的专业用户，可以继续把这个 Skill 调到可用、可控、可维护

## 1.1 导航与入口要求

该能力的顶部一级导航必须叫：

- `Skills`

不建议叫：

- `Skill`
- `Skill 工作台`

原因：

- `Skills` 更符合对象域命名
- 这个入口承载的不只是单个 Skill 编辑，还包括新建、生成、调优、测试、历史和与工作流相关的入口
- `Skill 工作台` 更适合作为 `Skills` 域内的核心页面名

## 2. 核心原则

## 2.1 对话负责“形成”

对话适合做：

- 需求澄清
- 初稿生成
- 模块定位
- 小范围修改建议

对话不适合直接承担：

- 全量结构维护
- 深度规则调优
- 复杂工作流编排
- 严格验证

## 2.2 深度调优必须结构化

深度调优必须具备：

- 可定位到具体模块
- 可局部修改
- 可验证
- 可对比
- 可回退

因此系统必须提供结构化编辑与验证，而不能只靠聊天。

## 2.3 编排建立在可调 Skill 之上

工作流编排不是第一步。

先要有：

- 一个结构化 Skill
- 一个可验证的 Skill
- 一个可以被单独调优的 Skill

然后才进入工作流编排。

## 3. 目标用户

## 3.1 小白用户

特征：

- 业务人员
- 不懂文件结构
- 不懂 YAML / Markdown / Prompt
- 想快速把想法变成可运行 Skill

核心目标：

- 通过自然语言做出完整 Skill
- 用最少配置完成一次上线前准备

## 3.2 专业用户

特征：

- AI 工程师
- AIBP
- 懂业务逻辑和流程设计的人

核心目标：

- 精细调规则
- 编排工作流
- 做验证和回放
- 稳定迭代版本

## 3.3 审核与管理用户

特征：

- 业务负责人
- 审核人
- 管理员

核心目标：

- 只看重点变化
- 快速评估风险
- 审批和回退

## 4. 产品模式

## 4.1 小白模式：对话生成

小白模式用于把“需求描述”转成完整 Skill 草稿。

输入：

- 一段自然语言需求
- 可选背景信息
- 可选参考 Skill / 模块

输出：

- 一个完整 Skill 草稿
- 自动生成的参数、规则、输出表格、测试样例
- 可选生成一个初步工作流草稿

## 4.2 专业模式：结构化调优与编排

专业模式用于把已生成的 Skill 做深入调整。

输入：

- 当前 Skill
- 模块级修改意图
- 参考历史执行结果
- 测试样例

输出：

- 模块 patch
- 验证报告
- 更新后的 Skill
- 更新后的工作流

## 5. 核心对象定义

## 5.1 Skill

Skill 在系统中的最小结构应包含：

- 基本信息
- 目标
- 规则
- 参数
- 输出表格
- 测试样例
- 关联工作流

## 5.2 模块

模块是系统中最小可编辑单元。

建议固定模块：

- `目标`
- `规则`
- `参数`
- `输出表格`
- `测试样例`
- `工作流`

## 5.3 Patch

Patch 是单次修改的最小单位。

一个 patch 只允许修改一个模块。

Patch 必须包含：

- 修改目标模块
- 修改摘要
- 结构化修改内容
- 风险提示
- 验证结果

## 5.4 验证结果

验证结果是 patch 是否可应用的依据。

它至少包括：

- 结构验证结果
- 样例验证结果
- 历史回放对比

## 5.5 工作流

工作流是 Skill 节点之间的有向编排。

工作流对象至少包含：

- 节点
- 连线
- 条件
- 节点输入输出映射

## 6. 功能总览

## 6.1 功能一：对话生成完整 Skill

### 目标

让小白用户通过自然语言生成一个可运行的完整 Skill 草稿。

### 输入

- 用户自然语言描述
- 可选行业/部门/场景
- 可选示例数据
- 可选参考模块

### 输出

- Skill 标题与目标
- 初步规则
- 参数列表
- 输出表格
- 测试样例

### 关键行为

1. 系统提炼需求
2. 系统识别缺失信息
3. 只在必要时追问
4. 生成完整 Skill 草稿
5. 用户确认后进入专业模式或保存草稿

### 边界

- 不保证一次生成就是最佳版本
- 生成完成后必须允许进入结构化调优

## 6.2 功能二：模块导航

### 目标

让所有用户都知道当前 Skill 可以按哪些模块调。

### 功能要求

- 页面必须显示模块导航
- 当前模块有明确高亮
- 每个模块显示当前状态
  - 未生成
  - 已生成
  - 待完善
  - 已验证

### 模块状态定义

- `空`
- `草稿`
- `已修改未验证`
- `验证通过`
- `验证失败`

## 6.3 功能三：模块定向对话编辑

### 目标

让用户用一句话只修改一个模块。

### 功能要求

- 用户可显式指定模块
  - 例：“只改参数”
- 用户可不指定模块，由系统自动推断
  - 例：“这个结果太激进了”
- 系统必须在不确定时做一次澄清
- 系统只生成单模块 patch

### 支持的对话修改场景

- 调整参数
- 改规则条件
- 改输出字段和展示方式
- 补测试样例
- 改工作流节点

### 不允许的行为

- 一轮对话同时改多个模块
- 直接静默重写整个 Skill

## 6.4 功能四：引用式编辑

### 目标

支持用户引用已有 Skill 或模块做针对性编辑。

### 功能要求

- 支持引用当前 Skill 某模块
- 支持引用其他 Skill 某模块
- 支持引用工作流中的某个节点输出
- 引用必须明确标记来源

### 典型用法

- “参考库存模块的规则”
- “沿用审批节点配置”
- “复制这个输出表格，但简化为 4 列”

### 系统行为

- 只加载被引用模块，不加载无关全文
- 只生成目标模块 patch

## 6.5 功能五：结构化专业编辑

### 目标

让专业用户摆脱聊天限制，直接编辑结构化内容。

### 功能要求

- 每个模块都有结构化编辑视图
- 支持表单、表格、节点图等专业控件
- 支持对比当前版本与上个版本
- 支持撤销本轮 patch

### 专业编辑入口

- 参数表
- 规则编辑器
- 输出表格编辑器
- 测试样例编辑器
- 工作流画布

## 6.6 功能六：输出表格定义

### 目标

把 Skill 输出从“纯文本回答”变成可运营、可下游消费的结构化表格。

### 功能要求

- 支持定义输出字段
- 支持字段说明、格式、接收人、优先级
- 支持预览最终展示效果
- 支持给工作流下游节点引用字段

### 输出表格必须支持

- 列名
- 字段类型
- 展示格式
- 接收对象
- 是否关键字段

## 6.7 功能七：工作流编排

### 目标

让专业用户把多个 Skill 或步骤组织成完整流程。

### 功能要求

- 允许新增节点
- 允许删除节点
- 允许拖拽排序
- 允许配置条件边
- 允许配置节点输入输出映射

### 工作流对话支持

用户可以说：

- “在这里插一个审批节点”
- “只有红灯才进入这个节点”
- “把这个输出表格给下游”

系统返回的仍然必须是结构化 workflow patch。

## 6.8 功能八：验证中心

### 目标

让每次修改都能被验证，而不是靠猜。

### 功能要求

- 结构验证
- 样例验证
- 历史回放验证
- before / after 对比

### 输出要求

验证中心必须清楚告诉用户：

- 哪些样例变好了
- 哪些样例变坏了
- 哪些历史记录受影响
- 是否建议应用

## 6.9 功能九：版本与回退

### 目标

让用户敢改、能撤销、能审查。

### 功能要求

- 每次 patch 独立保存
- 每次 patch 有 diff
- 每次 patch 有验证结果快照
- 可一键回退到任一 patch 前状态

## 6.10 功能十：角色化视图

### 小白用户视图

- 只看对话和简化预览
- 默认不展示复杂结构和工作流细节
- 用“应用修改”而不是“提交 patch”

### 专业用户视图

- 可看结构化数据
- 可直接编辑模块
- 可看工作流画布
- 可看验证详情和回放结果

### 审核用户视图

- 只看目标模块差异
- 只看风险摘要和验证摘要
- 可快速通过/驳回

## 6.11 功能十一：个人图形化界面调整

### 目标

让每个用户都能把“自己在当前 Skill 上看到的运行/结果界面”调成适合自己的工作方式，同时不改变 Skill 本体、不影响其他用户、不绕过审核。

### 功能要求

- 系统基于当前 Skill 的 input/output contract、`param_ui_schema`、`result_ui_schema` 自动生成图形化界面。
- 用户可以用自然语言要求 AI 调整当前界面，例如字段分组、图表类型、表格列顺序、指标卡组合、默认视图。
- AI 只能修改当前用户当前 Skill 当前 surface 的个人 UI overlay。
- AI 输出只能是声明式 UI schema / JSON Patch / overlay，不能生成或执行前端代码。
- 个人 overlay 只保存为 `user_id + skill_id + surface` 维度偏好，不写 Skill Git，不影响其他用户。
- 用户自定义 AI 调整提示词只保存为该 `user_id + skill_id + surface` 的个人默认提示词，下次打开该 Skill 时回填，不影响其他用户或 Skill 默认。
- 如果要把个人界面变成 Skill 默认界面，必须转为受控 UI patch，进入 Skill Git、验证、审核、发布链路。

### 不允许的行为

- AI 调整其他 Skill 的界面。
- AI 读取无权限字段、平台密钥、Cookie、MCP env、业务原始数据或其它用户 overlay。
- 个人 UI AI 从 `.env` 读取或写入模型 key；必须使用后台 `SystemConfig ai.*` 配置。
- AI key 返回前端、进入个人 overlay、run trace、执行参数或日志。
- AI 新增数据源、MCP scope、trigger、工作流、Skill 逻辑、可见性、发布态。
- 个人默认参数静默变成团队默认参数。

### 审计要求

用户执行 Skill 时，系统必须记录：

- `ui_pref_id`
- `ui_pref_version`
- `base_skill_commit`
- `merged_ui_schema_hash`
- 实际提交的 `params`

这样 run trace 可以还原用户当时看到的界面、默认值和最终提交参数。

## 7. 页面定义

所有页面应默认从顶部 `Skills` 导航进入，而不是作为 Skill 详情页的附属入口。

## 7.1 页面一：Skill 生成页

功能：

- 输入需求
- 对话澄清
- 生成 Skill 草稿
- 预览模块结果

适用角色：

- 小白用户
- AIBP

默认入口：

- 顶部一级导航 `Skills`
- `Skills` 首页中的“新建 / 生成”

## 7.2 页面二：Skill 工作台

功能：

- 模块导航
- 定向对话修改
- 结构化编辑
- diff 预览
- 验证结果

适用角色：

- 专业用户

默认入口：

- 顶部一级导航 `Skills`
- 从 `Skills` 列表或生成结果进入某个 Skill 的工作台

## 7.3 页面三：工作流画布页

功能：

- 节点编排
- 条件边配置
- 节点输入输出映射
- 节点级调优入口

适用角色：

- 专业用户

默认入口：

- 顶部一级导航 `Skills`
- 从 `Skills` 域内切换到 `工作流` 视图

## 7.4 页面四：验证页

功能：

- 测试样例结果
- 历史回放结果
- before / after 对比
- 风险提示

## 8. 关键交互流程

## 8.1 小白生成流程

1. 用户输入需求
2. 系统提炼成 Skill 草稿
3. 系统展示模块预览
4. 用户确认或补充
5. 保存为 Skill 草稿
6. 可进入专业模式继续调优

## 8.2 定向修改流程

1. 用户描述问题
2. 系统判断目标模块
3. 生成模块 patch
4. 展示 diff
5. 运行验证
6. 用户点击应用

## 8.3 专业编排流程

1. 用户进入 `工作流` 模块
2. 通过画布或对话修改节点
3. 系统生成 workflow patch
4. 展示结构 diff
5. 运行流程结构验证
6. 用户确认应用

## 9. 非功能要求

## 9.1 可解释性

每次修改都要告诉用户：

- 这次改了哪个模块
- 为什么这么改
- 会影响什么

## 9.2 可控性

任何 AI 生成结果都不能直接落盘，必须先预览。

## 9.3 可维护性

所有生成结果优先存结构化对象，不直接依赖长文本 prompt。

## 9.4 可扩展性

未来可扩展：

- 跨 Skill 模块引用
- 模块模板库
- 自动推荐工作流
- 多轮验证策略

## 10. MVP 定义

第一版建议只交付：

- 对话生成完整 Skill 草稿
- 模块导航
- 定向对话修改 `参数 / 规则 / 输出表格 / 工作流`
- patch 预览
- 样例验证
- 工作流简单节点编排
- 图形化界面的 schema 渲染器收口
- 当前用户当前 Skill 的个人 UI overlay 保存与恢复默认

先不做：

- 多 Skill 自动编排
- 全链路自动优化
- 复杂多角色协作机制
- 高阶自动推荐系统
- 任意前端代码生成或运行
- 个人 overlay 自动提升为 Skill 默认界面

## 11. 成功标准

功能上线后，至少应达到：

- 小白用户能通过对话做出完整 Skill 草稿
- 专业用户能不用聊天，直接进入模块化调优
- 每次修改都可验证、可预览、可回退
- 工作流编排建立在已可调的 Skill 之上
- 对话不再承担深度调优本身，而只是进入调优的入口
- 每个用户可以只调整自己在当前 Skill 上看到的图形化界面，且不会影响其他用户或其他 Skill
- AI 个人界面调整不会突破统一 Skill 权限，不会生成任意前端代码

## 12. 一句话总结

这个功能的定义不是：

`对话生成 Skill`

而是：

`通过对话形成完整 Skill，再通过结构化编辑、验证和工作流编排完成专业化深度调优。`
