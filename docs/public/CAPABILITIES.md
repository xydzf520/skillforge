## 3. 一条业务流程怎样交付

下面以“经营异常分析”为合成示例，展示角色与记录如何串联；数据源和具体 Skill 由使用者配置。

1. **定义目标与验收**：业务负责人给出指标口径、例外、输出、负责人及必须确认的动作，记录当前人工基线。
2. **建立能力**：产品与开发团队将说明实现为 Skill、Playbook 或项目应用；配置工具和数据合同，固定提示词与测试案例。
3. **验证版本**：用合成数据验证正常、缺失、错误和重复场景，保存 Git 版本，提交审核。预览或模拟通过不等于真实业务验证。
4. **发布与部署**：经审核版本发布到授权范围和节点。分别查看平台发布版本、节点接收版本、定时配置和具体运行状态。
5. **实际执行**：员工手动运行，或配置好的节点按计划执行；自建 Harness 通过同一授权接口参与，回传运行与产物。
6. **形成报告与待办**：结果进入报告和待办，负责人复核依据、修改建议或拒绝，并记录原因。业务写入与通知遵循对应接口规则。
7. **核实业务结果**：区分已生成、已发送、已读、已确认和实际业务完成；在可取得回执时记录，未知结果保持未知。
8. **选择改进层**：数据缺失修数据，知识过期更新知识，步骤不合理改流程，表达不合适改提示词；有可靠样本和评估目标后再考虑训练。
9. **验证下一版**：固定新版本与基准，对照质量、人工复核、异常和成本；审核后投入使用，观察结果并保留回滚路径。

这条链路同时存在三种生命周期：**资产版本**（草稿、审核、发布），**执行任务**（等待、运行、失败、完成），**业务结果**（建议、确认、执行、核实）。界面中的一个“完成”不能替代另两种状态。

## 4. 自建 Harness 的两层含义

**仓库内部的编排基础**：AgentCore 使用 LangGraph 组织意图、风险、生成、工具绑定、预览与发布检查，并提供检查点和人工中断恢复；Playbook 与执行服务负责组合任务及节点调度。这些是自建业务运行框架的组成部分，不等于已经提供一个适配任意 Agent 的通用运行器。

**企业自建的外部 Harness**：可以自行组织 Agent 循环、上下文与工具选择，通过 SDK/API/MCP 使用授权能力，通过兼容节点协议接收任务并回传结果。适配需要处理身份、超时、取消、幂等、版本和错误含义，不能只完成一次模型调用就宣布接入完成。

建议用同一运行标识关联：业务目标 → 输入及来源 → Skill/提示词/模型版本 → 工具调用 → 人工确认 → 产物 → 实际结果。不同模块的关联完整度应逐条核验；这份关联清单是集成验收要求，并非声称每条现有路径已经记录全部字段。

## 5. 企业资产应怎样管理

| 资产 | 应保留的内容 | 验收方法 |
|---|---|---|
| 工作流 | 步骤、依赖、负责人、输入输出、审批边界、失败处理 | 用正常、异常和中断恢复案例验证 |
| 提示词 | 目标、标准、变量、正反例、模型参数、版本与哈希 | 相同样本比较变更前后；将生效版本关联调用 |
| Skill | 定义、代码、工具范围、测试、版本、发布与节点状态 | 确认执行的是已审核版本，保留可回溯记录 |
| 日志与反馈 | 输入来源、工具行为、输出、用户纠正、业务结果和未知项 | 区分模拟／真实、成功／失败、推断／确认，检查敏感性与保留期限 |
| 知识、样本与评估集 | 来源权限、质量、时间、内容哈希、版本和用途 | 复核过期知识、重复数据、训练评估泄漏及错误标签 |
| 私有模型 | 基座依据、样本版本、训练参数、产物哈希、评估、部署与回滚 | 对照原模型和人工标准，测算质量、延迟及全成本 |

强模型可帮助产生候选，企业保留经过业务验证的标准和结果。日志中的所有文本都不应自动变成正确答案；失败案例及人工修正的价值需要明确标注。知识更新、技能修改和权重训练分别验收，避免把数据积累量当作学习效果。

## 6. 如何判断企业应用是否有效

建议选择同一任务范围和统计周期，记录样本数、失败及未知项，再对照改造前基线。

- **质量**：任务验收通过率、关键错误、返工和人工纠正；保留分母与抽样方式。
- **效率**：端到端耗时、人工复核时间、异常处理时间；不能只计算模型响应速度。
- **成本**：模型调用、算力、存储、运维及人工成本；平台 usage 估算只覆盖其中一部分。
- **采用与复用**：实际使用人数、覆盖团队、重复使用和复用版本；不能由访问页面或调用次数推导业务收益。
- **可控性**：错误能否定位、动作能否确认、重复是否被处理、版本能否撤回，恢复后结果是否一致。

上述是业务测量方案，项目中有看板、运行和用量数据基础；不宣称安装后就具备完整 ROI 测量或财务核算。

## 7. 本次识别出的实现限制

这些属于后续工程验收项，本次文档补齐没有将它们标为已修复。

| 项目 | 代码现状与影响 | 后续完成标准 |
|---|---|---|
| 提示词默认版本 | `PromptRegistry.set_default` 写进程内字典；管理接口记审计，未持久化选择。重启或多进程可能出现不同默认值 | 持久化、版本冲突处理、多进程刷新及调用版本回溯；补齐所有需要管理的调用入口 |
| 优化器版本隔离 | 控制器评测期间临时替换共享 `SKILL.md` 再恢复；runner 未显式向执行器传入不可变候选版本 | 在独立快照执行，并核对节点实际版本；不影响同时发生的编辑或生产运行 |
| 优化器模拟结果 | 节点调用异常会回退本地模拟，模拟参与断言及汇总；通过不代表真实节点执行改善 | 模拟与真实分开统计，真实晋升要求真实执行和独立评估证据 |
| 跨模型检查 | 未配置副模型或副模型失败时记录 skipped / secondary_failed，但不阻断主流程 | 业务自行定义哪些发布必须复核；明确跳过状态，不能把跳过当作一致性验证成功 |
| 模型训练评估 | 本地运行器含小规模留出生成检查；平台按配置门槛核对回传指标 | 扩充独立业务基准、同源去重、原模型比较和上线观察 |
| 备份恢复 | `scripts/backup_db.sh` 仅导出数据库，使用固定容器和路径，也未启用管道失败检查 | 改为可配置、失败可见的备份，纳入 Skill Git、配置及文件资产，并完成隔离恢复验证 |
| 公共发布与生产 | 项目已选用 Apache-2.0；权属与第三方分发范围、部分依赖审计、目标 Docker 与外部服务仍有待核对或验收 | 按发布边界逐项确认、升级复测、验证部署和恢复后再发布 |

查看实现：[提示词](../../app/common/prompt_registry.py)、[优化控制器](../../app/optimizer/controller.py)、[基准执行](../../app/optimizer/benchmark_runner.py)、[副模型检查](../../app/agent_core/nodes/cross_model_check.py)、[备份脚本](../../scripts/backup_db.sh)。以上判断来自代码路径核对，不包含真实生产故障复现。

## 8. 从本地演示到企业试点

| 阶段 | 应获得的结果 |
|---|---|
| 本地启动 | 独立凭据、数据库迁移、网页入口、独立 Skill 仓库与合成示例可用 |
| 授权试点 | 指定负责人、最小数据范围、模型和节点；打通一条真实只读任务和人工处理 |
| 小范围运行 | 验证版本、重试、外部动作回执、成本、权限与异常恢复；完成备份恢复演练 |
| 模型改进 | 准备有效样本与评估集，训练、比较、审核部署并观察业务结果 |
| 扩大使用 | 在质量与成本证据基础上增加部门、能力和节点，并检查权限、容量和维护责任 |

公开项目展示建议使用合成数据，沿“需求与设计 → 能力实现 → 审核部署 → 运行证据 → 改进”演示。个人职责与成果应另有证明；开源准备状态、模型训练能力和真实业务效果不能混写。
